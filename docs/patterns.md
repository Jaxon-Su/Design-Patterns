# C++ 設計模式中文說明

## 建立型 Creational

### Abstract Factory
簡介：建立一整組相容物件，而呼叫端不用知道具體類別。

問題情境：當系統有多個「產品族」時，如果到處都用 `new` 建立具體類別，切換產品族會變得很痛苦。例如 UI 同時有 Button、Checkbox、Dialog，深色主題與淺色主題不能混在一起。

模式核心精神：把「建立哪一系列物件」集中到工廠介面，讓呼叫端只依賴抽象產品。它主要解決的是產品族切換造成的具體類別耦合。

適合用在：同一套系統需要切換不同產品族，例如深色/淺色 UI 元件、不同儀器品牌的 Driver 物件。

原創例子：`ThemeFactory` 同時產生 Button 與 Checkbox，確保都是同一種主題。

### Builder
簡介：把複雜物件的建造步驟拆開，最後再組成完整結果。

問題情境：有些物件不是幾個建構子參數就能說清楚，可能需要標題、圖表、表格、格式、輸出設定。如果把所有組合塞進建構子，呼叫端會難讀，也容易傳錯順序。

模式核心精神：把「建造流程」和「最終物件」分離，用清楚的步驟累積狀態。它主要解決的是複雜建構流程與建構參數爆炸。

適合用在：建構參數很多、步驟有順序、不同組合會得到不同物件。

原創例子：`ReportBuilder` 逐步加入標題、圖表、表格，最後輸出報告。

### Factory Method
簡介：父類別定義建立物件的流程，子類別決定實際建立哪一種產品。

問題情境：框架或基底流程知道自己需要某種物件，但不應該知道具體類別。若父類別直接建立具體產品，未來新增產品時就要修改父類別。

模式核心精神：把物件建立延後到子類別，讓共同流程依賴抽象產品。它主要解決的是「流程固定，但產品類型會變」的耦合。

適合用在：框架知道「何時需要產品」，但不知道「該用哪個具體產品」。

原創例子：不同 `LogisticsApp` 建立卡車或無人機配送任務。

### Prototype
簡介：用複製既有物件來建立新物件，避免重新設定複雜初始狀態。

問題情境：某些物件建立成本高，或初始化狀態很繁瑣。若每次都從零開始設定，很容易漏掉欄位，也會讓呼叫端知道太多初始化細節。

模式核心精神：把「如何複製自己」交給物件本身，呼叫端只拿原型複製再微調。它主要解決的是重複初始化與建立成本問題。

適合用在：物件建立成本高，或有一批只差少數欄位的配置。

原創例子：複製一份預設感測器設定，再改成不同站點名稱。

### Singleton
簡介：確保全系統只有一個共用實例，並提供全域存取點。

問題情境：有些資源在概念上只能有一份，例如全域設定、唯一硬體連線、應用程式層級的服務。若到處建立多份，狀態可能互相衝突。

模式核心精神：把建構子藏起來，讓類別自己控制唯一實例的建立與存取。它主要解決的是唯一資源的一致性，但也會引入全域狀態耦合。

適合用在：全域唯一資源，例如設定中心、硬體連線管理器。請避免濫用，否則會讓測試與依賴關係變硬。

原創例子：`AppConfig` 儲存程式啟動後的環境名稱。

## 結構型 Structural

### Adapter
簡介：把既有類別的介面轉成呼叫端期待的介面。

問題情境：新系統期待一種乾淨介面，但舊系統或第三方 SDK 提供的是另一種介面。若呼叫端直接配合舊介面，舊格式會污染整個系統。

模式核心精神：在兩個不相容介面中間放一層轉接器，把差異封裝在邊界。它主要解決的是介面不相容造成的耦合。

適合用在：新系統要接舊 API、第三方 SDK、硬體函式庫。

原創例子：舊溫度 API 回傳華氏，Adapter 提供攝氏介面。

### Bridge
簡介：把抽象層與實作層分離，兩邊可以各自擴充。

問題情境：當一個類別同時有兩個會變動的維度，用繼承硬組合會快速膨脹。例如遙控器有一般版、進階版，設備也有電視、投影機、音響。

模式核心精神：用組合連接抽象與實作，讓功能抽象和平台實作分開演化。它主要解決的是多維度變化造成的類別爆炸。

適合用在：功能維度與平台維度會各自成長，例如通知內容與傳送通道。

原創例子：`RemoteControl` 操作不同種類的 `Device`。

### Composite
簡介：把單一物件與物件群組用同一種介面處理。

問題情境：樹狀結構裡，有些節點是葉節點，有些節點是容器。如果呼叫端每次都判斷「這是單一物件還是群組」，邏輯會到處重複。

模式核心精神：讓葉節點與組合節點實作相同介面，呼叫端用一致方式操作整棵樹。它主要解決的是階層結構中的特殊判斷與遞迴耦合。

適合用在：樹狀結構，例如 UI 元件、檔案系統、組織架構。

原創例子：資料夾包含檔案與子資料夾，計算總大小時使用同一介面。

### Decorator
簡介：在不修改原類別的情況下，動態加上額外行為。

問題情境：功能可能任意疊加，例如飲料加牛奶、珍珠、椰果；資料流加壓縮、加密、記錄。若每種組合都做成子類別，類別數量會爆炸。

模式核心精神：讓裝飾器和被裝飾物實作同一介面，並用包裝方式在前後加行為。它主要解決的是功能組合變化與繼承膨脹。

適合用在：功能可以層層疊加，例如壓縮、加密、快取、記錄。

原創例子：飲料先有基底，再加牛奶與珍珠。

### Facade
簡介：提供簡單入口，封裝背後複雜子系統。

問題情境：子系統通常有很多類別與呼叫順序，外部模組若直接操作全部細節，會對內部流程高度依賴。日後子系統調整時，外部也跟著壞。

模式核心精神：提供一個高階入口，讓常用流程變簡單，並把複雜協調留在 Facade 裡。它主要解決的是外部模組對子系統細節的耦合。

適合用在：外部只需要常用流程，不需要碰所有細節。

原創例子：`VideoExportFacade` 封裝載入、編碼、寫檔。

### Flyweight
簡介：共享大量物件中重複不變的內部狀態，節省記憶體。

問題情境：系統要建立大量相似小物件，若每個物件都保存相同資料，記憶體會浪費很多。例如地圖上成千上萬棵樹，樹種與貼圖其實大量重複。

模式核心精神：把可共享的不變資料抽出來集中管理，個別物件只保留不同的外部狀態。它主要解決的是大量重複狀態造成的記憶體成本。

適合用在：大量小物件，例如文字字元、地圖標記、棋盤格。

原創例子：地圖上多個樹木共享同一份樹種資料，只保存座標差異。

### Proxy
簡介：用代理物件控制對真實物件的存取。

問題情境：真實物件可能很昂貴、需要權限、位於遠端，或不希望呼叫端直接接觸。如果呼叫端自己處理這些控制邏輯，商業邏輯會變髒。

模式核心精神：代理物件實作和真實物件相同的介面，在轉交呼叫前後加入控制。它主要解決的是存取控制、延遲載入與遠端細節耦合。

適合用在：延遲載入、權限檢查、遠端呼叫、快取。

原創例子：`ImageProxy` 第一次顯示時才載入大型圖片。

## 行為型 Behavioral

### Chain of Responsibility
簡介：讓請求沿著處理鏈傳遞，直到某個物件能處理。

問題情境：一個請求可能由不同層級或不同角色處理。若呼叫端用大量 `if/else` 決定誰負責，新增處理者或調整順序都會牽動呼叫端。

模式核心精神：把每個處理者串成鏈，每個節點只決定自己能不能處理，不能就交給下一個。它主要解決的是請求發送者與處理者之間的直接耦合。

適合用在：審核流程、事件處理、例外分類。

原創例子：客服單依嚴重程度交給一線、工程師或主管。

### Command
簡介：把一個操作包成物件，方便排程、撤銷、重做與記錄。

問題情境：按鈕、選單、快捷鍵或工作佇列都可能觸發同一種操作。若觸發者直接呼叫接收者方法，就很難做 undo、重做、排程或記錄歷史。

模式核心精神：把「要做什麼」封裝成 Command 物件，觸發者只負責執行命令。它主要解決的是操作發起者與操作執行者之間的耦合。

適合用在：UI 按鈕、巨集、工作佇列、undo/redo。

原創例子：文字編輯器把「加入文字」包成 Command。

### Interpreter
簡介：為簡單語言或規則定義語法樹，並讓每個節點知道如何解釋自己。

問題情境：系統需要支援一組簡單規則，例如條件篩選、公式判斷、權限條件。若所有規則都寫成硬編碼 `if/else`，新增規則會讓程式越來越難維護。

模式核心精神：把規則拆成可組合的表達式物件，並讓每個節點負責解釋自己的語意。它主要解決的是簡單語法規則與業務流程混在一起的耦合。

適合用在：規則固定且不太複雜的小型 DSL，例如條件篩選、公式判斷、查詢語法。若語言會變得很大，通常應改用 parser 或現成規則引擎。

原創例子：用表達式判斷一筆訂單是否符合「金額大於 1000 且客戶是 VIP」。

### Iterator
簡介：不用暴露容器內部結構，就能逐一走訪元素。

問題情境：呼叫端想走訪集合，但不應該知道集合底層是陣列、鏈結串列、樹，還是資料庫查詢結果。如果暴露內部結構，容器一改，呼叫端也要跟著改。

模式核心精神：把走訪邏輯封裝成 Iterator，讓集合提供一致的巡覽方式。它主要解決的是集合內部結構與使用者之間的耦合。

適合用在：自訂集合需要提供穩定走訪方式。

原創例子：播放清單提供下一首歌曲。

### Mediator
簡介：把多個物件之間的複雜互動集中到中介者。

問題情境：多個物件彼此互相通知時，關係容易變成網狀。例如表單欄位、按鈕、錯誤訊息互相影響，最後每個元件都知道太多其他元件。

模式核心精神：讓元件只和 Mediator 溝通，由 Mediator 協調彼此反應。它主要解決的是多物件互相引用造成的高耦合。

適合用在：UI 控制項互相影響、聊天室、模組協調。

原創例子：登入表單由 `LoginDialog` 協調帳號欄、密碼欄與登入按鈕。

### Memento
簡介：保存物件狀態快照，之後可以還原。

問題情境：系統需要復原狀態，但又不想讓外部直接讀寫物件內部欄位。例如文字編輯、草稿保存、流程回復，都需要安全地保存某個時間點。

模式核心精神：由原物件產生狀態快照，外部只負責保存快照，不理解內部細節。它主要解決的是狀態還原需求與封裝性之間的衝突。

適合用在：undo、版本回復、暫存編輯狀態。

原創例子：草稿文件儲存歷史版本。

### Observer
簡介：主體狀態改變時，自動通知所有訂閱者。

問題情境：一個資料來源改變後，很多地方都要同步更新。若主體直接呼叫每個具體對象，新增或移除訂閱者都要修改主體。

模式核心精神：主體只維護抽象訂閱者清單，狀態變化時廣播通知。它主要解決的是資料來源與多個反應者之間的一對多耦合。

適合用在：事件系統、資料綁定、訊號通知。

原創例子：股票價格更新後通知手機 App 與儀表板。

### State
簡介：物件在不同狀態下有不同反應，狀態本身封裝行為。

問題情境：物件行為取決於目前狀態時，程式常會出現大型 `switch` 或 `if/else`。狀態越多，每個操作都要重複判斷，新增狀態也容易漏改。

模式核心精神：把每個狀態變成獨立類別，由狀態物件決定當下行為與狀態轉移。它主要解決的是狀態變化造成的條件判斷散落。

適合用在：流程狀態機，例如訂單、連線、播放器。

原創例子：播放器在停止與播放狀態下，按下 play 的行為不同。

### Strategy
簡介：把可替換演算法封裝起來，執行時選擇策略。

問題情境：同一件事有多種做法，例如不同折扣、排序、路徑規劃或匯出格式。若每次都在主流程用條件判斷選演算法，主流程會越來越胖。

模式核心精神：把演算法封裝成可替換策略，主流程只依賴策略介面。它主要解決的是演算法變化與使用流程之間的耦合。

適合用在：排序、折扣、路徑規劃、資料匯出格式。

原創例子：購物車結帳時套用會員折扣或節慶折扣。

### Template Method
簡介：父類別固定演算法骨架，子類別填入特定步驟。

問題情境：多個流程大致相同，但其中幾個步驟不同。若每個子類別都重寫整個流程，重複程式多，流程順序也可能不一致。

模式核心精神：在父類別保留流程骨架，把可變步驟留給子類別實作。它主要解決的是流程重複與流程順序不一致。

適合用在：流程固定但細節不同，例如資料匯入、測試流程、報表生成。

原創例子：不同飲品共用「煮水、沖泡、倒杯」流程，但沖泡內容不同。

### Visitor
簡介：把作用在物件結構上的新操作獨立出來，避免修改元素類別。

問題情境：物件結構已經穩定，但常常需要增加新的操作，例如計算、匯出、檢查、列印。若每次新增操作都改所有元素類別，會破壞穩定結構。

模式核心精神：把操作搬到 Visitor，元素只接受拜訪並回呼正確方法。它主要解決的是穩定資料結構與常變操作之間的耦合。

適合用在：物件結構穩定，但常增加新操作。

原創例子：圖形物件可被面積計算 Visitor 與匯出 Visitor 拜訪。
